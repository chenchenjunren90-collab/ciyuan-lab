# 协作与开发流程

## 1. 工作方式

团队以 Gitee Issue 为任务入口，以 `contracts/` 为协作边界，以 Pull Request 为唯一合并入口。每项任务只有一名人类负责人；AI可以辅助分析、编码、测试和文档，但不拥有合并权限和最终责任。

```text
Issue与验收标准
  → 契约/课程Schema先行
  → 独立短期分支
  → 实现与本地验证
  → PR与证据
  → 项目证据完整性检查（不自动评分）
  → develop联调
  → 演示验收
  → main发布
```

## 2. 任务拆分

一个Issue应由一人主责，并形成可独立评审、可验证的结果。跨模块需求拆成父Issue和子Issue，例如“Python Debug学习流程”拆为：

1. 课程负责人提交知识点、练习和判定规则；
2. 集成负责人冻结请求/响应契约；
3. 后端实现练习执行和画像更新；
4. 前端按Mock契约实现界面；
5. AI/RAG负责人补充检索和反馈编排；
6. 跨模块测试验证完整流程。

多人并行的是子任务，不是同时修改同一文件。

每个可领取的 Issue 必须写清：唯一负责人、输入提供人、最终验收与合并人、前置依赖、允许修改的目录、明确不处理的范围、具体产物、验收命令和下游交接。普通成员任务的最终验收与合并人固定为成员1。只有标题和一句“完成某功能”的 Issue 不得进入“进行中”。详细待办见 [单人 Issue 执行手册](collaborator-issues.md)。

## 3. 接口协作

- 公共接口、Schema和错误码只在 `contracts/` 定义；
- 当前 OpenAPI 只有健康检查与能力清单，业务接口必须先补充契约再实现，不能根据聊天记录临时拼字段；
- 前后端先用固定Mock联调，不等待所有后端逻辑完成；
- 课程包遵循统一Schema，通用引擎不得为单门课程复制分支；
- 每次契约变更都要更新契约测试和使用方；
- 不兼容变更在合并前由架构负责人确认。

后端内部端口以以下文件为唯一来源：

- `apps/api/app/modules/rag/ports.py`；
- `apps/api/app/modules/model_adapters/ports.py`；
- `apps/api/app/modules/orchestration/ports.py`；
- `apps/api/app/modules/practice/ports.py`。

这些 Python 端口不是 HTTP 接口。前端只通过 `contracts/openapi.yaml` 中已经评审的接口访问后端；课程包只提供数据，不直接导入后端模块。

## 4. PR大小和评审

- 一个 PR 只解决一个 Issue；
- 每个 PR 从 `docs/templates/pr-six-part-description.md` 复制一份独立 Markdown 说明到 `docs/presentation/`，包含“作品阐述、功能思路、技术方案、运行效果、迭代计划、创新之处”；总汇总文档由成员1在合并后统一提炼，避免多人修改同一文件；
- 优先提交可运行的小PR，不积累三周后一次合并；
- 评审重点依次为：需求正确、边界安全、契约一致、测试充分、代码可读；
- 普通成员 PR 统一由成员1验收和合并，普通成员不得自审或自合并；
- 成员1自己的 PR 必须记录差异复核、全量检查结果、风险和回退方式，证据齐全后可以自行验收合并；
- 课程事实、算法结论和来源不确定时，成员1可要求对应领域成员在 Issue 评论中提供依据，但不增加共同实现者；
- 模型输出示例不是测试证据，需使用固定输入、Schema与确定性断言；
- 公共契约、数据安全、代码执行限制不得在“临时演示修复”中绕过。

## 5. Issue状态与协作

- Issue看板只保留“待办、进行中、待评审、已完成”；
- 每人同时进行中的编码Issue不超过一个；
- 开始编码前写明负责人、修改目录、依赖接口和验收命令；
- 出现阻塞时直接记录在Issue中，并关联所依赖的Issue或PR；
- 接口分歧写入ADR或Issue结论，不通过口头约定绕过契约；
- 联调只基于远程分支和PR，不通过私聊发送无法追踪的代码包。

## 6. 课程成员支援前端与 AI/RAG

成员4、5、6在本课程知识点目录通过验收、当前课程Issue无阻断返修并提交统一课程交接包后，可以领取成员2或3拆出的支援Issue。支援不改变目录所有权：

1. 默认先贡献 Mock、课程展示样例、黄金问答、预期引用、代码事实和验收用例；
2. 如需实际修改 `apps/web/**` 或成员3主责目录，支援Issue必须列出允许修改的具体文件和冻结接口；
3. 支援Issue只有一名实现负责人，成员2或3提供领域接口并接收结果，最终 PR 仍由成员1验收合并；
4. 支援者不得自行新增课程专用HTTP字段、页面分支、智能体、提示词流程或模型适配器；
5. 范围变化时另建子Issue；公共契约变化另建契约Issue，实际使用方在评论中提供需求，成员1负责最终验收；
6. 三门课程必须使用同一交接模板和同一 `course_id` 驱动流程，不能各自约定接口。

课程成员可以因此承担第二、第三分工中的一部分具体工作，但成员2仍对统一学习体验负责，成员3仍对检索、模型和智能体行为负责。

## 7. 集成顺序

1. `contracts/` 与课程包Schema；
2. Mock与测试夹具；
3. 后端模块；
4. 前端交互；
5. 外部模型和RAG；
6. 完整流程与降级测试；
7. 演示数据和部署。

这样即使外部模型临时不可用，也可以使用固定响应展示数据库、课程、代码验证和学习闭环，而不让整个演示失效。

## 8. 发布条件

- 只有通过验收的Issue才能随PR合入 `develop`；
- 从 `develop` 发布到 `main` 前，必须建立发布Issue并列出纳入范围；
- 发布前从零启动一次环境并跑通三门课程的代表性完整流程；
- 演示账号、脱敏数据和模型配额单独检查；
- 已知限制写进发布Issue和演示说明，不用临时代码隐藏。
