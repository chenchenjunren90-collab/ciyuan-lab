# 课程包统一标准

## 1. 目标

C、Python、数据结构三门课程由不同成员并行建设，但平台只能维护一套读取、检索、测评和画像更新逻辑。所有课程必须基于 `course_packs/_template/`，差异通过数据和受控执行配置表达，不复制业务代码。

## 2. 推荐结构

```text
course_packs/<course>/
  manifest.yaml              课程元数据、版本、状态与内容统计
  concepts/                  每个知识点一个YAML/JSON文件，含学习卡
  exercises/                 客观题、代码题、Debug任务与评价规则
  projects/                  课后综合练习及其非敏感样例数据
  sources/                   经授权资料清单与片段元数据
```

三门课程的目录与文件Schema必须完全一致。新增公共字段时先更新 `_template/` 和校验脚本，再迁移三个课程包。

## 3. 知识点最小字段

```yaml
id: PY-FUNC-01
title: 函数定义与调用
course: python
schema_version: 0.1.0
version: 1
difficulty: beginner
estimated_minutes: 30
prerequisites: [PY-BASE-03]
learning_objectives:
  - 能定义带参数和返回值的函数
concepts: [参数, 返回值, 作用域]
lesson:
  summary: 使用函数封装可复用逻辑，并通过参数接收输入、返回值输出结果。
assessment_ids: [PY-FUNC-01-Q1, PY-FUNC-01-C1]
source_refs: [SRC-PY-TEXTBOOK-04]
status: reviewed
```

要求：

- `id` 发布后不复用、不随标题变化；
- 前置关系不得形成环；
- 学习目标使用可观察、可测量的动词；
- 每个知识点至少关联一个测评；
- `source_refs` 必须指向已登记资料；
- 未经人工审核使用 `draft`，不得进入默认学习路径。

## 4. 练习类型与判定

| 类型 | 适用场景 | 主要判定方式 |
|---|---|---|
| 客观题 | 概念识别与基础理解 | 标准答案/规则 |
| 简答题 | 解释思路与比较 | 评分要点 + 模型辅助，标明非绝对判定 |
| 代码题 | 编程与算法实现 | 编译/运行 + 公开及隐藏测试 |
| Debug | 错误定位与修复 | 目标测试 + 错误类型标签 |
| 综合练习 | 多知识点应用 | 确定性结果 + 分项Rubric + 人工/模型反馈 |

代码题至少定义语言版本、入口、输入输出、时间/内存限制、公开示例、隐藏测试分类和禁止能力。模型生成的解释不得改变测试通过情况。

## 5. 首期内容深度

每门课程首期约40个核心知识点，分两层建设：

- **全量基础层**：每个知识点具有完整元数据、学习卡、来源和至少一个测评映射；
- **重点实践层**：优先选择8—12个高频或高难知识点，提供代码、Debug、递进提示和高质量反馈；
- **综合应用层**：每门至少一个覆盖多个知识点的课后综合练习。

这种分层保证三门课程都有完整结构，同时将有限时间投入最能展示学习闭环的内容。

## 6. 财经管理场景规则

财经场景只能出现在 `projects/` 或明确标记的课后综合练习中：

```yaml
scenario_scope: post_course_finance_practice
scenario_provider: tuoling
data_classification: authorized_desensitized
computer_science_objectives:
  - 使用Python完成数据清洗与异常值处理
business_context_objective:
  - 理解字段含义并解释结果限制
```

- 评价核心仍是程序设计、算法、数据处理和调试能力；
- 驼灵提供背景、字段解释或业务约束，不替学生完成代码；
- 不适合财经化的知识点不强行加入财经包装；
- 示例数据必须为合成、公开或经授权脱敏数据；
- 无授权或来源不确定时使用仓库固定的合成案例。

## 7. 内容审核

课程负责人自检后，由另一课程负责人审核结构与表达；涉及算法正确性由数据结构负责人复核；涉及财经含义、授权与驼灵调用由AI/RAG与数据负责人复核。所有修改保留版本和评审记录。

## 8. 课程包交接与 RAG 入库

课程包合入 `develop` 只代表课程内容通过审核，不代表已经写入向量知识库。课程内容与 RAG 入库分属两个独立 Issue：

1. 课程负责人完成课程包并通过内容互审；
2. 课程负责人按 `HANDOFF-C`、`HANDOFF-PY` 或 `HANDOFF-DS` 提交统一交接包；
3. AI/RAG 负责人先在 `RAG-01` 中实现来源读取、分块、向量化、索引和引用回传，再对满足前置条件的课程执行入库；
4. 对应课程负责人使用 `RAG-ACCEPT-C`、`RAG-ACCEPT-PY` 或 `RAG-ACCEPT-DS` 的黄金问答集审核课程事实与预期来源；
5. 检索实现与课程事实均通过后，才可在对应 `RAG-ACCEPT-*` Issue 中记录该课程“RAG 可用”。

本节规定交接责任，不表示当前仓库已经具备完整入库能力。截至初始骨架，后端只有 `KnowledgeRetriever.search(...)` 查询端口；入库接口、分块策略、向量模型、索引迁移和可运行命令均由 `RAG-01` 实现并测试，不得由三门课程各自开发一套。

### 8.1 课程负责人交付什么

每门课程使用同一份交接清单：

- `course_id`、课程包提交号、各内容版本、课程负责人和审核人；
- 3—5个代表性知识点 ID、一个知识卡、一道客观题、一道代码题或 Debug 题、一个综合练习；
- 经授权的来源登记及 `source_refs`；
- 至少5个黄金问题及各自预期来源；
- 至少1个“依据不足，应拒答或降级”的问题；
- 至少1个错误引用样例；
- 正确代码、错误代码及预期确定性验证结果；
- 一条课程入口到下一任务的演示路径和已知限制。

在交接包 Schema 尚未由 `ARCH-02` 冻结前，上述材料附在对应 Gitee Issue 中；冻结后必须使用 `course_packs/_template/` 中的统一格式，三门课程不得自行增加字段或目录。

### 8.2 AI/RAG 负责人处理什么

AI/RAG 负责人只处理已经登记且获准使用的资料，负责：

- 读取并校验课程、来源和知识点标识；
- 按统一策略进行内容分块与向量化；
- 将 `course_id`、`source_id`、`chunk_id`、内容版本和定位信息写入索引元数据；
- 提供可按课程过滤的检索结果与可核验引用；
- 在资料缺失、分数不足或来源不可用时返回受控降级，而不是编造答案；
- 记录固定黄金问答集的测试结果，使后续版本可以回归比较。

课程负责人审核内容事实和预期来源；AI/RAG 负责人对分块、索引、检索、引用与降级行为负责。模型输出不得替代来源审核，也不得覆盖编译和测试结论。

### 8.3 入库与验收证据

`RAG-01` 实现完成且入库格式已由 `ARCH-02` 冻结后，每次入库至少留下以下可复现证据：

- 使用的课程包提交号与各内容版本；
- 入库命令或自动化任务标识；
- 成功、跳过和失败的来源/片段数量；
- 重复执行或版本更新时的幂等/重建行为；
- 黄金问题、预期 `source_id/chunk_id` 与实际结果；
- 依据不足、错误引用和过期版本的处理结果；
- 不含密钥、真实个人信息、未授权资料和未经脱敏业务数据的检查记录。

在 `exercises/`、`projects/`、`sources/` 的正式 Schema 与引用校验尚未由 `ARCH-02` 落地前，课程包校验脚本只能验证知识点基础字段、ID、manifest 计数一致性和前置关系等已有规则。`assessment_ids` 与 `source_refs` 的目标是否真实存在仍需人工互审，不能仅凭脚本通过宣称“可入库”。
