# 六人岗位分工与独立交付说明

本文件用于把“谁负责什么、交付给谁、什么算完成”固定下来。团队采用单人负责制：一个 Issue 只有一名实现负责人、一个独立分支和一个 PR；Gitee 的“协作者”字段保持为空。每项任务的可复制描述见 [单人 Issue 执行手册](collaborator-issues.md)。

## 1. 当前基线：MVP v0.3 完整演示版

截至 2026-08-26，仓库已经完成 MVP v0.3 并部署公网演示环境：

- C语言42个、Python40个、数据结构40个知识点已经录入统一课程包；
- OpenAPI 已覆盖诊断、计划、课程学习、RAG 问答、练习/代码验证、画像更新、推荐和综合项目；
- 学情规划、课程辅导、质量监督三个逻辑智能体已接入统一编排，生产环境使用讯飞 MaaS，外部模型不可用时明确降级；
- PostgreSQL/pgvector、Redis、学习记录与画像持久化、混合检索和 Docker 隔离代码验证已经集成；
- 三门课程共用一套前后端闭环，Python 另有阶段重测、结构化学习卡和自适应变式题完整样板。

当前基线是可演示、可验证的竞赛初步版本，不等同于生产级教学系统。课程内容仍保持 `draft`，尚未完成课程教师正式审核；统一身份认证、教师后台、生产监控和大规模并发不在本版本范围。后续新增或修改公共接口仍须先建立 Issue，更新 `contracts/openapi.yaml` 和契约测试，再进入实现。

任何成员都不能只以“目录存在”或“模型能返回文本”作为完成证据。完成必须同时提供实现、测试/校验、文档和可复现的演示证据。

## 4. 各成员可执行职责

### 成员1：架构、后端底座与集成负责人

**主责内容**

- 维护公共 API、学习事件、共享 Schema、统一错误码与版本策略；
- 建立 PostgreSQL/pgvector、Redis、迁移、种子数据和学生内部标识规则；
- 实现画像持久化、基于证据的掌握度更新规则和下一任务所需的数据服务；
- 维护本地启动、环境配置、集成测试、CI 检查和 `develop` 演示候选版；
- 主持契约冻结和跨模块联调，解决跨模块冲突，但不代替其他成员完成其业务内容。

**接口输入/输出**

| 输入 | 输出 |
|---|---|
| 已合入 `develop` 的页面字段样例、智能体/RAG 结构、`VerificationResult` 夹具和三门课程包数据 | `contracts/openapi.yaml` 中经过完整验收的 HTTP JSON；`contracts/events/learning-event.schema.json` 格式的学习事件；可查询的画像/学习记录；统一错误与可启动环境 |

`LearningEvent.student_id` 只能使用平台内部不透明标识。公共契约先提交 Schema、示例和测试；成员1自己的契约 PR 必须记录全量检查、使用方输入和回退方式后才能自行验收，不能口头改变字段后要求其他人追赶。

**主要联调对象**：成员2（API消费者）、成员3（智能体/RAG）、成员4（代码验证）；课程数据问题分别找成员4/5/6。

**不得越界**：不得决定课程知识点和答案；不得把单门课程特殊逻辑写进公共 API；不得在 API 进程直接执行学生代码；不得在没有契约测试和验收证据时单方面改公共契约；不得成为所有任务都必须等待的“唯一编码者”。

### 成员2：前端与学习体验负责人

**主责内容**

- 实现统一学生端：课程选择、初始测评、计划、知识卡、RAG问答、代码/Debug、结果、画像与下一步；
- 根据 OpenAPI 建立统一请求层、类型和错误处理，先用 Mock 与固定夹具开发；
- 三门课程通过 `course_id` 和课程包配置复用组件，不复制三套页面；
- 明确加载、空数据、超时、依据不足、模型降级和代码运行失败状态；
- 准备演示路径与前端自动化/组件测试证据。

**接口输入/输出**

| 输入 | 输出 |
|---|---|
| `contracts/openapi.yaml`、课程元数据、计划/引用/验证/画像响应、成员1提供的 Mock | 符合契约的 HTTP 请求；可复现的页面状态；对 `source_id/chunk_id`、测试事实、推荐理由的清晰展示；前端错误与重试行为 |

前端只通过 HTTP API 访问后端，不直接导入后端模块，不直接连接数据库，也不直接调用讯飞或驼灵。

**主要联调对象**：成员1（API与数据）、成员3（模型状态/引用）、成员4（代码验证反馈）、成员4/5/6（课程展示抽查）。

**不得越界**：不得在页面硬编码知识点、答案和课程特例；不得由前端判断代码是否通过；不得在浏览器保存模型密钥；不得绕过 `contracts/` 自创字段；不得为了好看隐藏失败、依据不足或降级状态。

### 成员3：AI、RAG 与智能体负责人

- 实现学情规划、课程辅导、质量监督三个逻辑智能体的结构化编排，不拆成三个服务；

**接口输入/输出**

| 端口/输入 | 必须输出 |

**不得越界**：不得让模型直接写数据库画像；不得让模型覆盖编译/测试结论；不得为每门课程复制智能体；不得伪造引用或把“模型知道”当来源；不得把姓名、学号、完整学习日志、密钥或未授权资料发给外部模型；不得把驼灵扩展成财经问答中心。

## 6. 单人交付与验收关系

### 统一规则

- 一个 Issue 只有一名实现负责人，Gitee“协作者”字段保持为空；
- 一个 Issue 对应一个从最新 `develop` 创建的独立分支和一个 PR，PR 目标为 `develop`；
- 每人同时最多只有一个“进行中”的编码 Issue；
- 成员2—6的 PR 统一由成员1·陈骏人验收和合并，普通成员不得自审或自合并；
- 成员1自己的 PR 只有在逐项复核差异、全量检查通过、PR记录验收证据和回退方式后才可自行验收合并；
- 任何人不得以私聊或口头约定替代仓库中的 Schema、Mock、夹具、示例和测试证据；
- 缺少字段、跨目录修改或范围扩大时另建小 Issue，不临时扩成多人共同开发；
- 外部模型不可用时必须能切换到 Mock/降级路径，不能阻断核心学习闭环。

## 7. 课程成员完成主责后的支援机制

成员4、5、6的课程包工作相对独立，完成当前主责后可以继续支援成员2的前端和成员3的 AI/RAG。支援的目的，是利用课程负责人最熟悉知识点、题目和来源的优势加速联调；不是取消成员2、3的领域所有权，也不是让多人随意修改同一目录。

### 7.1 进入支援的条件

课程负责人同时满足以下条件后，才能领取支援 Issue：

1. 本课程的 `CONTENT-*-03` 已验收，交接引用的知识点、练习、综合项目和来源均已合入并通过课程包校验；
2. 自己当前领取的课程 Issue 已合入或进入“待验收”，且没有尚未处理的阻断性修改意见；
3. 本课程 `handoff.yaml` 已按统一格式通过成员1验收，代表性代码样例可由确定性验证链路复现；
4. Gitee 上已经建立独立支援 Issue，写明唯一负责人、允许修改的文件、依赖接口、验收命令，并由成员1最终验收合并。

不按完成日期判断是否可以支援，也不要求三位课程负责人同时切换。谁先满足条件，谁先领取当前最有价值的支援 Issue。

成员4同时主责通用代码验证，因此不能只因 C 课程目录完成就转去支援；如果 `PRACTICE-*` 仍阻断成员2、3或三门课程联调，应先完成验证器主责。成员5、6没有同等程度的底层模块主责，通常更适合优先领取前端夹具、黄金问答集和课程验收类支援 Issue。

### 7.2 两种合法支援方式

**方式A：交付数据与验收材料，默认优先使用。**

- 支援前端：提供三课程统一格式的 Mock 数据、页面文案样例、正常/空数据/错误状态、代码验证预期和内容准确性验收清单；
- 支援 RAG：提供授权来源、黄金问题、预期 `source_id/chunk_id`、依据不足问题、错误引用样例和课程事实依据；
- ARCH-02 合入后，课程事实与验收样例必须写入各课程的 `handoff.yaml`；负责人、最终验收人、前端状态夹具等流程信息分别保存在 manifest、Gitee Issue/PR 和下游验收文件中，不得私自加入 `handoff.yaml` 顶层字段。

**方式B：承担成员2或3拆出的有边界实现子 Issue。**

- Issue 必须逐项列出允许修改的文件；课程负责人只能改这些文件，不能顺手重构整个 `apps/web/**` 或 AI/RAG 模块；
- 公共 HTTP 字段仍先改 `contracts/openapi.yaml`；内部端口仍以 `ports.py` 为准。支援者不得自行增加只服务一门课的字段、页面分支、智能体或适配器；
- 支援 Issue 的具体实现者是唯一负责人；成员2或3提供领域接口和接收意见，不与实现者共同修改分支；最终 PR 仍由成员1验收合并；
- 如果范围扩大，立即停止原 Issue，另建子 Issue 或契约变更 Issue，不用口头约定扩大修改范围。

### 7.3 统一课程交接包

三门课程使用完全相同的交接清单：

| 类别 | 必须交付的内容 |
|---|---|
| 身份 | `handoff.yaml` 保存 `course_id` 与 `package_revision`；负责人在 manifest，最终验收与合并人在 Gitee Issue/PR |
| 展示样例 | `handoff.yaml` 引用3—5个代表性知识点ID、一道客观题、一道代码/Debug题和一个综合项目 |
| 前端状态 | 正常、加载、空数据、验证失败、模型降级样例由 `WEB-ACCEPT-*` 使用统一 Mock/契约文件维护，不写入 `handoff.yaml` |
| RAG验收 | 至少5个黄金问题及预期来源、至少1个依据不足问题、至少1个错误引用样例 |
| 代码事实 | 正确代码、错误代码、预期 `VerificationResult`；算法题另含边界与复杂度期望 |
| 演示与限制 | 一条从课程入口到下一任务的路径，以及当前不支持的能力 |

课程交接包只描述课程事实和预期，不替代前端组件、检索引擎或模型适配器。机器校验会确认 `assessment_ids`、`source_refs` 等引用目标存在且类型一致，但不能证明课程事实、答案、测试设计或授权声明真实正确；课程负责人仍须留下证据，由成员1检查记录。

### 7.4 支援 Issue 与责任关系

| Issue | 实现负责人 | 最终验收与合并人 | 交付重点 |
|---|---|---|---|
| `HANDOFF-C / HANDOFF-PY / HANDOFF-DS` | 成员4 / 5 / 6 | 成员1 | 按统一清单形成三门课程交接包 |
| `WEB-ACCEPT-C / PY / DS` | 成员2；如拆出子 Issue，则以子 Issue 指定者为唯一负责人 | 成员1 | 统一组件读取课程数据；展示事实正确；无课程硬编码 |
| `RAG-ACCEPT-C / PY / DS` | 成员3；如拆出子 Issue，则以子 Issue 指定者为唯一负责人 | 成员1 | 入库、检索、引用、依据不足在该课程上通过验收 |

遇到问题时按事实归属：课程文字、答案或来源错误由课程负责人修；数据正确但页面显示错误由成员2修；资料存在但检索不到或引用错位由成员3修；HTTP字段不一致由成员1组织契约修订；代码判定错误由成员4修；算法边界或复杂度错误由成员6复核。发现者负责提供可复现样例，不直接越权修改主责目录。

## 9. 每个人的完成定义

一项任务只有同时满足以下条件才算完成：

- Issue 验收项逐条有证据，不以“我写完了”作为状态；
- 修改范围符合目录所有权，公共契约和文档已同步；
- 正常、失败和边界路径至少各有一个测试或可复现检查；
- 课程内容有授权来源和负责人核对记录，代码题有确定性判定；
- 普通成员 PR 已由成员1验收并合并；成员1自己的 PR 已完成全量检查、差异复核、风险与回退记录；
- 普通成员没有审核或合并自己的 PR；Gitee 协作者字段为空；
- 演示所需 Mock/降级路径可用，不依赖某个人电脑或临时密钥；
- 不含真实个人信息、密钥、未授权资料或未经脱敏的财经数据；
- 仓库统一检查 `.\scripts\check.ps1` 通过；普通成员确实只能执行专项命令时，必须说明未执行全量检查的原因和风险；成员1自行验收的 PR 不适用该豁免。

## 10. 人员变化处理

本版本按六人设计。若有人缺席，先在 Gitee 中移除原负责人，再把边界清晰的 Issue 重新指派给备份人；协作者仍保持为空，不允许两人同时维护同一分支。若长期变为五人，优先压缩每门重点实践数量，不取消课程统一标准、确定性验证或安全边界。
