# 六人岗位分工与协作者执行说明

本文件用于把“谁负责什么、交付给谁、什么算完成”固定下来。团队成员姓名尚未最终对应时，Issue、分支、PR 和会议记录统一使用 `成员1`—`成员6`；确定后只填写下方映射表，不改变角色边界。每项任务的可复制描述见 [协作者 Issue 执行手册](collaborator-issues.md)。

## 1. 当前基线：这是可开发骨架，不是已完成产品

截至项目初始化，仓库已经具备统一目录、课程包模板、最小 OpenAPI/学习事件契约、前后端启动骨架、三智能体/RAG/画像/练习/模型适配端口、检查脚本和协作文档，但业务功能仍待实现：

- API 目前只有健康检查和能力清单；
- C、Python、数据结构课程 `manifest.yaml` 的 `implemented_core_concepts` 均为 `0`；
- 三个逻辑智能体、RAG、画像更新和代码验证当前主要是接口占位；
- 数据库、真实模型调用、完整学习闭环和三门课程内容需要六人按本文件并行完成。

当前 `contracts/openapi.yaml` 实际只定义健康检查和能力清单，测评、计划、问答、练习、画像与推荐接口都必须先由 Issue 提议、在 OpenAPI 中评审通过，再进入实现。内部 Python 端口也不是前端可直接调用的 HTTP 接口，不得把骨架中的类型当成已经冻结的完整业务协议。

因此，任何成员都不能把“目录存在”当作“功能完成”。完成必须同时提供实现、测试/校验、文档和可复现的演示证据。

## 4. 各成员可执行职责

### 成员1：架构、后端底座与集成负责人

**主责内容**

- 维护公共 API、学习事件、共享 Schema、统一错误码与版本策略；
- 建立 PostgreSQL/pgvector、Redis、迁移、种子数据和学生内部标识规则；
- 实现画像持久化、基于证据的掌握度更新规则和下一任务所需的数据服务；
- 维护本地启动、环境配置、集成测试、CI 检查和 `develop` 演示候选版；
- 主持契约冻结和跨模块联调，解决跨模块冲突，但不代替其他成员完成其业务内容。

**接口输入/输出**

| 输入 | 输出 |
|---|---|
| 成员2提出的页面数据需求；成员3提出的智能体/RAG结构；成员4提出的 `VerificationResult`；三门课程包数据 | `contracts/openapi.yaml` 中评审通过的 HTTP JSON；`contracts/events/learning-event.schema.json` 格式的学习事件；可查询的画像/学习记录；统一错误与可启动环境 |

`LearningEvent.student_id` 只能使用平台内部不透明标识。公共契约先评审、后实现；成员1不能口头改变字段后要求其他人追赶。

**主要联调对象**：成员2（API消费者）、成员3（智能体/RAG）、成员4（代码验证）；课程数据问题分别找成员4/5/6。

**不得越界**：不得决定课程知识点和答案；不得把单门课程特殊逻辑写进公共 API；不得在 API 进程直接执行学生代码；不得未经使用方评审单方面改公共契约；不得成为所有任务都必须等待的“唯一编码者”。

### 成员2：前端与学习体验负责人

**主责内容**

- 实现统一学生端：课程选择、初始测评、计划、知识卡、RAG问答、代码/Debug、结果、画像与下一步；
- 根据 OpenAPI 建立统一请求层、类型和错误处理，先用 Mock 与固定夹具开发；
- 三门课程通过 `course_id` 和课程包配置复用组件，不复制三套页面；
- 明确加载、空数据、超时、依据不足、模型降级和代码运行失败状态；
- 准备演示路径与前端自动化/组件测试证据。

**接口输入/输出**

| 输入 | 输出 |
|---|---|
| `contracts/openapi.yaml`、课程元数据、计划/引用/验证/画像响应、成员1提供的 Mock | 符合契约的 HTTP 请求；可复现的页面状态；对 `source_id/chunk_id`、测试事实、推荐理由的清晰展示；前端错误与重试行为 |

前端只通过 HTTP API 访问后端，不直接导入后端模块，不直接连接数据库，也不直接调用讯飞或驼灵。

**主要联调对象**：成员1（API与数据）、成员3（模型状态/引用）、成员4（代码验证反馈）、成员4/5/6（课程展示抽查）。

**不得越界**：不得在页面硬编码知识点、答案和课程特例；不得由前端判断代码是否通过；不得在浏览器保存模型密钥；不得绕过 `contracts/` 自创字段；不得为了好看隐藏失败、依据不足或降级状态。

### 成员3：AI、RAG 与智能体负责人

**主责内容**

- 实现授权资料的入库、分块、检索、来源回传和引用校验；
- 通过 `model_adapters/` 统一接入讯飞 MaaS/Agent，提供超时、有限重试、错误映射、Mock 和固定降级结果；
- 仅在授权、脱敏的课后经管综合练习中适配驼灵 API；
- 实现学情规划、课程辅导、质量监督三个逻辑智能体的结构化编排，不拆成三个服务；
- 校验模型输出 Schema、引用、敏感字段，以及反馈与确定性测试是否一致。

**接口输入/输出**

| 端口/输入 | 必须输出 |
|---|---|
| `KnowledgeRetriever.search(query, course_id, top_k)` | `SearchHit[]`，每条含 `source_id`、`chunk_id`、`content`、`score`、`metadata` |
| `ModelAdapter.complete(messages)` | 归一化 `ModelResponse`，含 `content`、`provider`、`model`、`usage`，异常转为统一错误或降级结果 |
| `LearningOrchestrator.next_activity(student_id, course_id)` + 画像、课程 ID、练习事实 | `PlannedActivity` 或经契约确认的结构化计划/辅导结果，只引用存在的知识点 ID 和可核验来源 |

**主要联调对象**：成员1（契约、画像与日志）、成员2（引用/状态展示）、成员4（测试事实）、成员4/5/6（课程来源和内容抽查）。

**不得越界**：不得让模型直接写数据库画像；不得让模型覆盖编译/测试结论；不得为每门课程复制智能体；不得伪造引用或把“模型知道”当来源；不得把姓名、学号、完整学习日志、密钥或未授权资料发给外部模型；不得把驼灵扩展成财经问答中心。

### 成员4：C 语言与代码验证负责人

**主责内容**

- 按统一模板建设 C 语言知识点、来源、测评、代码题和 Debug 任务；
- 实现 `practice/` 中与语言无关的验证编排，以及 C/Python 固定版本的编译/运行、测试映射和诊断；
- 与成员1共同定义隔离运行环境、无网络、超时、内存、输出和文件系统限制；
- 为正确、编译错误、运行错误、答案错误、超时和资源超限准备固定测试；
- 支持成员5/6复用验证能力，不为 C 单独复制一套业务流程。

**接口输入/输出**

| 输入 | 输出 |
|---|---|
| `language`、`source_code`、`limits`、练习的公开/隐藏测试和判定规则 | `VerificationResult { accepted, passed_tests, total_tests, diagnostics }`；诊断必须脱敏、限长、可复现 |

**主要联调对象**：成员1（运行隔离、API与日志）、成员2（结果展示）、成员3（基于测试事实生成反馈）、成员5（Python测试）、成员6（算法测试）。

**不得越界**：不得在 FastAPI 进程或宿主机无隔离执行学生代码；不得开放网络或任意文件访问；不得把语言模型作为代码裁判；不得为方便演示取消资源限制；不得强行给指针、内存等基础知识套财经背景；不得修改其他课程包内容。

## 6. 固定互审与联调关系

### 必须评审

- 成员1的公共 API/数据变更：成员2（前端消费）和对应领域成员至少一人评审；
- 成员2的学生主流程：成员1评审接口一致性，课程页面由对应课程负责人抽查；
- 成员3的模型/RAG/智能体变更：成员1评审契约与日志，涉及课程来源时由对应课程负责人评审；
- 成员4的验证器：成员1评审隔离与资源限制，成员3评审模型反馈不得篡改测试事实；
- C ↔ Python：成员4和成员5互审课程结构、表达与测评可执行性；
- 数据结构：成员5审结构与教学表达；成员6复核 C/Python 中的算法和复杂度内容。

### 联调规则

- 联调只以远程 `develop` 最新提交为基线，不通过聊天软件传递代码包；
- 每人同时只能有一个“进行中”编码Issue，完成或交付评审后再领取下一个；
- 外部模型不可用时必须能切换到Mock/降级路径，不能阻断核心学习闭环；
- 出现阻断性接口分歧时暂停冲突实现，先在Issue或ADR中形成结论；
- 任何人不得审核并合并自己的PR，阻塞的PR由成员1重新指定评审人。

## 7. 课程成员完成主责后的支援机制

成员4、5、6的课程包工作相对独立，完成当前主责后可以继续支援成员2的前端和成员3的 AI/RAG。支援的目的，是利用课程负责人最熟悉知识点、题目和来源的优势加速联调；不是取消成员2、3的领域所有权，也不是让多人随意修改同一目录。

### 7.1 进入支援的条件

课程负责人同时满足以下条件后，才能领取支援 Issue：

1. 本课程的 `CONTENT-*-01` 已验收，约40个知识点目录、来源和测评映射通过课程包校验与交叉评审；
2. 自己当前领取的课程 Issue 已合入或进入“待评审”，且没有尚未处理的阻断性修改意见；
3. 已按统一格式准备本课程交接包，至少含代表性知识点、练习、正确/错误样例、来源和一条演示路径；
4. Gitee 上已经建立独立支援 Issue，写明唯一负责人、允许修改的文件、依赖接口、验收命令和成员2或3这一领域负责人的必审要求。

不按完成日期判断是否可以支援，也不要求三位课程负责人同时切换。谁先满足条件，谁先领取当前最有价值的支援 Issue。

成员4同时主责通用代码验证，因此不能只因 C 课程目录完成就转去支援；如果 `PRACTICE-*` 仍阻断成员2、3或三门课程联调，应先完成验证器主责。成员5、6没有同等程度的底层模块主责，通常更适合优先领取前端夹具、黄金问答集和课程验收类支援 Issue。

### 7.2 两种合法支援方式

**方式A：交付数据与验收材料，默认优先使用。**

- 支援前端：提供三课程统一格式的 Mock 数据、页面文案样例、正常/空数据/错误状态、代码验证预期和内容准确性验收清单；
- 支援 RAG：提供授权来源、黄金问题、预期 `source_id/chunk_id`、依据不足问题、错误引用样例和课程事实审核；
- 交接格式尚未在 `course_packs/_template/` 冻结前，材料先附在对应 Gitee Issue；冻结后只能使用统一模板，三门课程不得各创一套格式。

**方式B：承担成员2或3拆出的有边界实现子 Issue。**

- Issue 必须逐项列出允许修改的文件；课程负责人只能改这些文件，不能顺手重构整个 `apps/web/**` 或 AI/RAG 模块；
- 公共 HTTP 字段仍先改 `contracts/openapi.yaml`；内部端口仍以 `ports.py` 为准。支援者不得自行增加只服务一门课的字段、页面分支、智能体或适配器；
- 成员2或3仍是相应目录的领域负责人，负责方案确认、代码评审、集成验收与是否合并；支援 Issue 的具体实现者是唯一主负责人；
- 如果范围扩大，立即停止原 Issue，另建子 Issue 或契约变更 Issue，不用口头约定扩大修改范围。

### 7.3 统一课程交接包

三门课程使用完全相同的交接清单：

| 类别 | 必须交付的内容 |
|---|---|
| 身份 | `course_id`、课程包版本、负责人、审核人 |
| 展示样例 | 3—5个代表性知识点ID、一个知识卡、一道客观题、一道代码/Debug题、一个综合练习 |
| 前端状态 | 正常、加载、空数据、验证失败、模型降级各一个预期样例 |
| RAG验收 | 至少5个黄金问题及预期来源、至少1个依据不足问题、至少1个错误引用样例 |
| 代码事实 | 正确代码、错误代码、预期 `VerificationResult`；算法题另含边界与复杂度期望 |
| 演示与限制 | 一条从课程入口到下一任务的路径，以及当前不支持的能力 |

课程交接包只描述课程事实和预期，不替代前端组件、检索引擎或模型适配器。机器校验当前尚不能确认 `assessment_ids` 和 `source_refs` 对应文件一定存在，因此课程负责人仍须人工核对并留下评审记录。

### 7.4 支援 Issue 与责任关系

| Issue | 实现主负责人 | 必须评审/验收 | 交付重点 |
|---|---|---|---|
| `HANDOFF-C / HANDOFF-PY / HANDOFF-DS` | 成员4 / 5 / 6 | 成员2、3 | 按统一清单形成三门课程交接包 |
| `WEB-ACCEPT-C / PY / DS` | 成员2；若拆出实现子Issue可由对应课程成员承担 | 成员2 + 对应课程成员 | 统一组件读取课程数据；展示事实正确；无课程硬编码 |
| `RAG-ACCEPT-C / PY / DS` | 成员3；黄金集子Issue可由对应课程成员承担 | 成员3 + 对应课程成员 | 入库、检索、引用、依据不足在该课程上通过验收 |

遇到问题时按事实归属：课程文字、答案或来源错误由课程负责人修；数据正确但页面显示错误由成员2修；资料存在但检索不到或引用错位由成员3修；HTTP字段不一致由成员1组织契约修订；代码判定错误由成员4修；算法边界或复杂度错误由成员6复核。发现者负责提供可复现样例，不直接越权修改主责目录。

## 9. 每个人的完成定义

一项任务只有同时满足以下条件才算完成：

- Issue验收项逐条有证据，不以“我写完了”作为状态；
- 修改范围符合目录所有权，公共契约和文档已同步；
- 正常、失败和边界路径至少各有一个测试/可复现检查；
- 课程内容有授权来源和另一课程负责人审核，代码题有确定性判定；
- PR由指定互审成员通过，已在最新 `develop` 上联调；
- 演示所需Mock/降级路径可用，不依赖某个人电脑或临时密钥；
- 不含真实个人信息、密钥、未授权资料或未经脱敏的财经数据。
- 仓库统一检查 `.\scripts\check.ps1` 通过；如只执行专项命令，必须说明未执行全量检查的原因并由评审人确认。

## 10. 人员变化处理

本版本按六人设计。若有人短期缺席，先由映射表中的备份人接手阻断集成的Issue，非关键内容顺延；若长期变为五人，优先压缩每门重点实践数量而不是取消课程统一标准、确定性验证或安全边界。任何合并角色都要在Gitee Issue中写明新的主负责人和缩减范围。
