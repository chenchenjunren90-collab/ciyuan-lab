# 单人 Issue 执行手册

本文直接写给六名项目成员，用来独立领取任务、在 Gitee 创建 Issue、通过仓库产物交付给下游并完成验收。本文不设置周计划或截止日期；任务是否可领取，只看前置依赖是否满足。

## 1. 使用方式

1. 先在 [六人岗位分工与独立交付说明](responsibilities.md) 中确认自己的成员编号和主责目录；
2. 从本文选择一个前置依赖已满足的 Issue，一次只领取一个“进行中”的编码 Issue；
3. 用 `.gitee/ISSUE_TEMPLATE.zh-CN.md` 创建 Gitee Issue，写清目标、范围、产物、验收项和最终验收与合并人；普通成员固定填写成员1·陈骏人，Gitee“协作者”字段保持为空；
4. 从最新 `develop` 创建独立分支，命名按 `feat/<issue>-<topic>`、`content/<issue>-<course>`、`test/<issue>-<topic>` 或 `docs/<issue>-<topic>`；
5. 一个 Issue 只对应一个分支和一个 PR，PR 必须关联 Issue 并合回 `develop`；
6. 实现负责人独立完成代码、测试和必要文档；普通成员 PR 由成员1在合并前复现验收，不进入作者分支共同修改；
7. 普通成员不得审核、验收或合并自己的 PR；成员1自己的 PR 在全量检查与验收证据齐全后可以自行验收合并；缺字段、跨目录修改或范围扩大时另建小 Issue；
8. 交接只使用已合入 `develop` 的 Schema、OpenAPI、Mock、夹具、示例和测试证据，不依赖私聊文件或口头字段。

输入提供人只在 Issue 评论中给材料或指出缺口，不是共同负责人，也不是最终合并人。普通成员 PR 的最终验收与合并人固定为成员1，且不得把任何人添加为 Gitee 协作者。

## 2. 全员必须遵守的统一标准

### 2.1 当前真实基线

| 项目 | 唯一依据 | 当前事实 | 协作规则 |
|---|---|---|---|
| HTTP API | `contracts/openapi.yaml` | 已冻结学习闭环 9 个接口（ARCH-01） | 测评、计划、问答、练习、画像和推荐接口已定义，运行时按契约子集推进实现 |
| 学习事件 | `contracts/events/learning-event.schema.json` | 已定义事件信封；`payload` 仍是无约束对象 | `student_id` 只能用平台内部不透明标识；事件载荷字段未冻结前不得口头约定 |
| 课程包 | `course_packs/_template/` 与 `docs/course-package-standard.md` | 三门课程均为 `0/40` 骨架 | 三门课程保持同一目录、字段、版本和状态规则 |

### 2.2 课程包统一格式

三个课程包都只能使用下列结构：

```text
course_packs/<course>/
  manifest.yaml
  concepts/
  exercises/
  projects/
  sources/
```

课程 ID 固定为 `c`、`python`、`data_structures`；知识点前缀固定为 `C-`、`PY-`、`DS-`。知识点至少包含 `id`、`title`、`course`、`schema_version`、`version`、`difficulty`、`estimated_minutes`、`prerequisites`、`learning_objectives`、`concepts`、`lesson.summary`、`assessment_ids`、`source_refs` 和 `status`。

校验器会检查 manifest、知识点、练习、项目、来源和 `handoff.yaml` 的结构，以及 ID、计数、前置关系、跨文件引用、运行声明和发布门禁。机器校验只能证明格式与引用一致，不能证明课程事实、答案、测试设计或授权声明真实正确；这些仍须由负责人提供证据并由成员1最终验收。

### 2.3 统一验收命令

所有 PR 合并前在仓库根目录执行：

```powershell
.\scripts\check.ps1
```

未激活虚拟环境时可执行：

```powershell
.\scripts\check.ps1 -Python .\.venv\Scripts\python.exe
```

专项快速检查不能代替全量检查；普通成员确实无法执行全量检查时，必须在 PR 中说明原因、已执行的命令和未覆盖风险。成员1自行验收的 PR 不适用该豁免。

### 2.4 统一验收映射

当前及后续任务统一使用以下关系：成员2—6的 PR 均由成员1·陈骏人最终验收并合并；成员1自己的 PR 在逐项检查差异、全量检查通过、记录验收证据与回退方式后自行验收合并。

下列表格最后一列记录“最终验收与合并人”和下游交接对象。任何领域专家的补充意见都通过 Issue 评论提供，不添加为协作者，也不形成多人验收门槛。

## 9. 课程成员何时以及怎样支援成员2、3

课程负责人可以支援，但必须同时满足以下入口条件：

- 本课程 `CONTENT-*-03` 和 `HANDOFF-*` 已验收；
- 当前课程 PR 已合入或处于待验收且无阻断返修；
- 已领取 `SUP-*-WEB` 或 `SUP-*-RAG`，或者成员2/3拆出的具体实现子 Issue；
- Issue 已列出允许修改的具体文件、冻结接口、验收命令，并明确成员1为最终验收与合并人。

支援优先顺序不是固定日期，而是“先消除当前集成瓶颈”：若页面缺稳定样例，先做 WEB 支援；若资料无法检索或引用无法验收，先做 RAG 支援；若本课程仍有阻断修改，先完成主责。

成员4还有代码验证主责：如果 `PRACTICE-*` 正在阻断三门课程联调，成员4先处理验证器。成员5、6在课程基础包验收后，通常可以更早承担 Mock、组件测试、黄金问答集和检索验收等支援工作。

### 支援中的责任边界

| 发生的问题 | 负责修复的人 |
|---|---|
| 知识点文字、答案、练习要求或来源本身错误 | 对应课程负责人 |
| 课程数据正确但页面渲染或交互错误 | 成员2 |
| 资料已登记但检索不到、排序异常或引用错位 | 成员3 |
| HTTP 字段、错误码或数据库记录不一致 | 成员1组织契约/数据修订 |
| 代码通过与否判断错误 | 成员4 |
| Python 题目的预期答案或测试设计错误 | 成员5在课程 Issue 修正；如验证器也有问题，由成员4另开独立 Issue 修正 |
| 算法边界、复杂度或标准结论错误 | 成员6 |
| 模型解释与确定性测试冲突 | 成员3负责输出门禁，成员4确认测试事实 |

发现者负责在 Issue 中提供最小复现数据，不直接进入别人的主责目录“顺手修复”。如果领域负责人明确拆出有边界子 Issue，支援者可以实际编码，但其 PR 仍由成员1最终验收合并，且不得与实现者共同修改同一分支。

## 10. Issue 完成定义

一个 Issue 同时满足以下条件才可关闭：

- Issue 中的验收项逐条附有测试输出、截图、请求响应或人工审核记录；
- 修改未超出列明的文件范围；公共契约、课程 Schema 和文档已同步；
- 正常、失败和边界路径均有证据，或明确说明为何不适用；
- 课程内容有授权来源与负责人核对记录；代码题有确定性测试；
- `.\scripts\check.ps1` 通过，或 PR 明确记录未执行部分及风险；
- 普通成员 PR 已由成员1验收并合并，普通成员没有自审或自合并；成员1自己的 PR 已完成全量检查、差异复核、风险和回退记录；
- 不含密钥、真实个人信息、未授权资料或未经脱敏的业务数据；
- 下游成员可以仅根据 Issue 和仓库内容复现，不依赖私聊文件或某个人电脑。
