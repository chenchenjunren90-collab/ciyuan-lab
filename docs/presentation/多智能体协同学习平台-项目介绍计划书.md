## 项目摘要

“多智能体协同学习平台”是一套面向计算机专业课程学习的智能助学系统。平台希望解决传统课程学习中“起点判断不准确、学习内容缺少个体适配、智能问答缺乏可靠来源、代码练习难以客观判定、学习结果无法进入下一步规划”等问题，将能力摸底、个性化规划、结构化学习、多角色辅导、代码实践、结果验证、学习画像更新和下一任务推荐连接成连续闭环。

平台不是让大模型代替教师或替学生完成作业，而是把大模型放入一套有课程边界、有证据来源、有验证机制、有失败降级的学习流程中。学情规划智能体负责决定“下一步学什么”，课程辅导智能体负责决定“当前内容怎么讲”，质量监督智能体负责检查“回答能否发布”；代码是否正确则由编译器、解释器、公开样例和服务器端测试共同判定，不由语言模型主观评分。

当前版本选择 Python 作为第一门完整打通的样板课程，已经形成从能力诊断到学习规划、沉浸课堂、课程问答、代码练习、结果验证、画像更新和下一任务推荐的端到端流程。平台的长期目标不是停留在 Python，而是沉淀一套可复用的计算机课程能力底座，后续按统一课程包规范逐步扩展到 C 语言、数据结构及其他计算机专业课程。

一句话价值主张：**让每一次回答、每一段代码，都成为下一步学习的证据。**

# 一、作品阐述

## 1.1 项目背景

计算机专业课程具有明显的知识前置关系和实践属性。学生是否真正掌握一项能力，不能只看是否听过某一章节，还要看其能否理解关键概念、完成代码练习、处理边界情况，并把知识迁移到新的任务中。

现有学习方式通常分散在教材、视频、作业平台、在线判题系统和通用 AI 问答工具之间。教材和视频结构稳定，却难以适配每名学生不同的基础；通用 AI 能快速解释问题，却可能脱离课程进度、缺少可靠引用，甚至把表面合理的代码误判为正确；在线判题能够判断结果，却通常不能解释学生为什么出错，也不会把错误转化为后续学习规划。

因此，本项目关注的不是“再增加一个可以聊天的入口”，而是建立一条适合计算机课程特点的连续学习链路：先判断学生当前会什么、缺什么，再安排学习内容和练习；学生完成真实操作后，用客观结果更新画像，最后据此重新计算下一步任务。

## 1.2 需要解决的核心问题

### 1.2.1 学习起点不准确

学生的知识结构往往不是线性的。例如，学生可能会使用列表推导式，却在循环边界、条件筛选或变量作用域上存在基础缺口。仅依据年级、章节进度或一次总分，很难发现这种“后面的内容会用、前置能力却不稳定”的情况。

### 1.2.2 学习内容缺少个体适配

固定课表要求所有学生从同一章节、以同一速度学习。基础较弱的学生可能跟不上，已有经验的学生又会重复学习。真正的个性化不应只改变推荐页面，而应同时影响学习起点、讲解密度、环节顺序、练习难度和时间预算。

### 1.2.3 智能答疑缺少课程边界和证据

通用模型可以生成流畅答案，但流畅不等于适合当前课程，也不等于有可靠依据。学生需要知道答案来自哪一份课程资料、是否符合当前学习阶段、资料不足时系统是否会拒答或降级，而不是把模型记忆当成课程事实。

### 1.2.4 代码学习缺少“解释与裁决”的合理分工

大模型适合解释报错、提供分级提示和帮助学生定位问题，但不能替代编译器、解释器和测试用例宣布代码正确。若让同一个模型同时生成答案、评价答案并更新画像，就会产生难以审计的闭环偏差。

### 1.2.5 学习行为没有转化为下一步依据

一次答题、一次提问或一次代码提交，如果只停留在聊天记录和结果页面中，就无法持续改善后续学习。平台需要将这些行为转换为结构化证据，用于更新学生画像、调整学习顺序和推荐下一项任务。

## 1.3 作品定位

本作品定位为：**面向计算机专业课程的多智能体协同学习平台**。

它具有三个明确边界：

1. 服务对象是正在学习计算机专业课程的学生，而不是面向所有领域的百科问答用户。
2. 核心任务是完成“测、学、问、练、验、评、再规划”的学习闭环，而不是追求无限对话。
3. 大模型只承担规划、解释、组织和反馈等适合语言模型的任务；课程事实、代码结果和画像更新分别受到知识库、测试系统与业务规则约束。

## 1.4 目标用户与使用场景

平台首期面向以下学生群体：

- 编程基础薄弱，需要分步骤讲解和即时反馈的学生；
- 有一定编程经验，但知识点之间存在前置断层的学生；
- 能理解概念，却难以独立完成代码任务和综合实践的学生；
- 希望根据个人时间、基础和学习偏好安排课程进度的学生。

典型使用场景包括：

- **课前摸底**：通过跨层级问题定位已有能力和缺失前置；
- **课中学习**：根据画像生成当前课堂，完成小步讲解、理解检查、角色问答和即时练习；
- **课后巩固**：完成代码题、Debug 任务和阶段重测；
- **长期学习**：依据真实学习证据更新画像，推荐下一任务并逐步进入综合项目。

# 二、功能思路

## 2.1 总体设计原则

平台以“证据驱动的学习闭环”为核心设计思路。每一个环节既服务当前学习，也为下一环节产生结构化输入。

```text
能力摸底
  → 形成初始学习画像
  → 学情规划智能体生成阶段目标和本次学习计划
  → 学生进入结构化课堂并进行多角色问答
  → 学生完成练习、Debug 或代码任务
  → 编译器、解释器和测试用例给出确定性结果
  → 课程辅导智能体解释结果并提供分级提示
  → 质量监督智能体检查证据、角色和反馈一致性
  → 业务规则更新学习画像
  → 重新计算下一任务
```

这一闭环强调两点：第一，学习结果必须能够被验证；第二，验证结果必须能够影响下一步，而不是一次学习结束后重新回到固定课表。

## 2.2 三智能体协同机制

平台后台设置三个职责稳定、可以分别测试的逻辑智能体。

| 智能体 | 主要输入 | 主要输出 | 明确不负责 |
|---|---|---|---|
| 学情规划智能体 | 测评结果、学习画像、知识前置、历史练习、时间和偏好 | 阶段目标、课堂组合、推荐顺序和推荐理由 | 不判定代码正确，不生成不存在的课程活动 |
| 课程辅导智能体 | 当前课程、学生问题、学习阶段、知识库证据、测试摘要 | 小步讲解、追问、分级提示、Debug 引导和总结 | 不伪造来源，不直接修改掌握度 |
| 质量监督智能体 | 学生原问题、角色、回答、引用、测试事实和安全状态 | 放行、拒绝或降级意见 | 不覆盖测试事实，不生成伪引用，不替代业务规则 |

三个智能体不是自由聊天的三个角色，而是同一学习流程中的三种职责。拆分的目的不是增加“智能体数量”，而是避免一个模型同时规划、回答和评价自己，使每一类输出都能被独立检查。

## 2.3 Python 样板课程的功能组成

### 2.3.1 跨层级能力摸底

能力摸底不以排名为目的，而是识别学习起点。题目覆盖不同层级知识，并提供“我不知道/还没有学过”选项，让学生可以诚实表达证据不足，避免猜测正确被误判为掌握。答案由服务器统一判定，前端不保存答案键。

### 2.3.2 学习画像与前置断层识别

系统将诊断、练习和代码验证结果转换为学习证据，记录学生在各知识节点上的当前状态。规划时既考虑已掌握内容，也检查薄弱节点是否是后续内容的前置条件，避免简单地从第一章重学或只按照总分推荐。

### 2.3.3 个性化学习规划

规划智能体综合使用服务器判分结果、历史练习、知识前置关系、每日可投入时间、每周学习天数和学习偏好，生成当前阶段目标和本次课堂组合。规划只能引用课程包中真实存在的知识点与活动，不允许临时虚构课程章节。

### 2.3.4 沉浸式结构化课堂

课堂采用“讲解一小段—理解检查—角色交流—代码练习—获得反馈”的节奏。沉浸感来自持续参与和及时反馈，而不是与学习无关的积分、战斗或剧情。课堂完成度与能力掌握度分开展示，避免学生因为“看完页面”就被视为已经掌握。

### 2.3.5 有来源的课程问答

学生提问后，系统先限定课程范围，再检索本地课程资料，由辅导智能体依据检索片段组织回答，并展示来源信息。资料不足、相关性过低或问题超出课程范围时，系统明确拒答或采用保守降级，不用模型常识填补证据空白。

### 2.3.6 分级提示与 Debug 引导

对于练习和代码问题，系统优先提供方向性提示，再逐步增加具体程度，帮助学生保留思考过程。模型可以解释错误、提出小实验或指出检查方向，但不直接宣布代码是否通过。

### 2.3.7 确定性代码验证

学生代码在受控环境中运行。页面可以展示公开样例，服务器保留隐藏测试，并返回编译错误、运行错误、超时、测试失败或通过等明确状态。只有测试链路确认通过后，系统才记录相应学习证据。

### 2.3.8 画像更新与下一任务推荐

每次有效学习事件都带有事件标识、证据类型和结果。业务规则根据证据更新掌握状态，同时保留更新前后数值、原因和策略版本。下一任务推荐以更新后的画像为依据，并向学生展示推荐理由。

## 2.4 前台角色与后台智能体的关系

课堂中可以设置教师、助教和同伴等不同表达角色，以承担讲解、提示、提问、共同 Debug 和总结等教学行为。它们是课程辅导智能体的受控表达方式，并不是额外增加的自治智能体。

所有前台角色必须共用同一课程知识链、同一引用规则和同一质量门禁。角色差异体现在教学行为和表达方式，而不能体现在课程事实是否一致。

## 2.5 典型用户流程

以一名首次进入 Python 课程的学生为例：

1. 学生完成能力摸底，并在不会的问题上选择“我不知道”。
2. 系统依据答题结果和知识前置关系生成初始画像，说明当前优势与薄弱点。
3. 学生填写每天可投入时间和偏好的学习方式，规划智能体生成本阶段目标与本次课堂。
4. 学生进入沉浸课堂，完成分段讲解、理解检查和角色交流。
5. 学生提交一段代码。第一次提交未通过隐藏测试，系统返回测试事实和分级提示。
6. 学生修改代码后再次提交，测试全部通过。
7. 通过结果写入学习证据，当前课堂保持稳定，完成后再更新画像。
8. 系统根据新画像推荐下一任务，并说明推荐原因。

这一流程适合作为比赛演示主线，因为它能够在一次真实任务中同时呈现多智能体协同、课程知识约束、代码验证和自适应推荐。

## 2.6 功能边界

- 平台不替学生直接完成作业或综合项目；
- 平台不把语言模型输出当作代码正确性的最终依据；
- 平台不在课程资料不足时用模型记忆补写课程结论；
- 平台不把尚未打通的课程写成已经完成；
- 平台不以一次问答效果代替完整学习效果；
- 平台不以界面存在代替功能通过真实流程验证。

# 三、技术方案

## 3.1 总体架构

竞赛阶段采用“前后端分离 + 模块化单体后端 + 三智能体编排 + 课程知识检索 + 确定性代码验证”的架构。采用模块化单体是为了优先保证闭环完整、部署稳定和接口可审核，后续只有在并发、故障隔离或团队边界出现明确需求时再拆分服务。

```text
Vue 3 / TypeScript / Vite 学生端
                ↓
FastAPI / Pydantic / OpenAPI 接口层
                ↓
学习流程编排层
  ├─ 学情规划智能体
  ├─ 课程辅导智能体
  └─ 质量监督智能体
                ↓
业务能力层
  ├─ Python 课程与知识检索
  ├─ 学习画像与任务推荐
  ├─ 练习、Debug 与代码验证
  └─ 学习事件与证据审计
                ↓
PostgreSQL / pgvector / Redis / 版本化课程包
                ↓
受控模型服务与隔离代码运行环境
```

## 3.2 前端交互层

前端负责展示课程、测评、规划、课堂、问答、代码编辑、验证结果、学习画像和下一任务。所有业务事实通过统一 API 获取，不在浏览器中硬编码答案、隐藏测试或模型密钥。

前端需要明确区分加载、成功、空数据、依据不足、模型降级、编译失败、运行失败和测试失败等状态。对学习系统而言，失败状态是否表达清楚与成功页面同样重要。

## 3.3 后端业务与接口层

后端使用 FastAPI 提供统一接口，以 Pydantic 和 OpenAPI 固定请求、响应、错误码和公共字段。课程、学生画像、问答、代码验证和智能体编排各自保持模块边界，但在一个后端进程中完成部署，降低竞赛版本的运维复杂度。

学习流程中的关键对象均采用结构化数据表达，例如课程 ID、知识点 ID、练习 ID、事件 ID、引用 ID、测试结果和推荐理由，从而避免只保存不可计算的聊天文本。

## 3.4 多智能体编排

三个智能体通过结构化输入输出协同，而不是依赖自然语言自由群聊。

- 规划输出必须引用现有课程活动，不能生成不存在的知识点 ID；
- 辅导输出必须关联课程证据或明确标记降级；
- 监督输出只能给出放行、拒绝或降级意见，不能改写测试结果；
- 模型返回必须通过 Schema、引用、安全和事实一致性检查；
- 模型不可用时，核心学习内容、代码验证和业务规则仍能继续运行。

## 3.5 课程知识库与可信问答

Python 课程内容以版本化课程包组织，记录知识目标、前置关系、学习顺序、例题、误区、练习和来源。课程资料经过分块后进入检索系统，每条片段保留来源标识、片段标识、标题、版本和授权状态。

学生提问的处理链路为：课程隔离、原问题检索、证据筛选、模型组织回答、引用校验、质量监督和本地发布门禁。若本地资料没有足够证据，系统应明确说明依据不足；对明确属于 Python 的问题，可以在白名单和访问数量限制下查询 Python 官方文档，但不跟随任意外链。

## 3.6 学习画像与证据更新

学习画像不是由大模型直接填写，而是由业务规则依据真实事件更新。证据可以来自能力摸底、普通练习和代码验证，不同证据具有不同权重。

每次更新至少记录：

- 学生内部匿名标识；
- 课程和知识点；
- 证据类型、证据值和来源事件；
- 更新前后状态；
- 策略版本与原因码；
- 事件是否已经处理，防止重复更新。

该机制保证画像可解释、可审计，也为未来评估更复杂的知识追踪方法保留数据基础。

## 3.7 代码验证与反馈分工

代码任务的处理顺序如下：

1. API 校验学生会话、课程、知识点和练习归属；
2. 代码进入隔离运行环境，默认关闭网络并限制时间、内存、进程、文件和输出；
3. 解释器或编译器执行公开样例和服务器端测试；
4. 系统得到通过数、错误类型和受控输出；
5. 辅导智能体结合测试事实和课程资料组织解释；
6. 监督智能体检查反馈是否与测试事实一致；
7. 业务规则依据结果更新画像并生成下一任务。

这一路线实现“模型负责解释，测试负责裁决”。即使模型给出的建议表述出现偏差，也不能改变代码的真实测试状态。

## 3.8 数据、安全与稳定降级

平台遵循数据最小化原则。向外部模型发送的信息不应包含姓名、学号、联系方式、完整学习记录、模型密钥或不必要的源代码。代码执行与主服务隔离，课程资料必须来源明确，模型输出必须经过结构和安全门禁。

系统需要具备以下降级路径：

- 模型不可用时，继续展示固定课程内容、代码测试事实和有明确标识的保守反馈；
- 检索无证据时，明确拒答或提示超出课程范围；
- 代码执行失败时，返回编译、运行、超时或资源限制状态，不无限重试；
- 生成式回答未通过监督时，替换为证据提取式回答，仍不合格则拒绝发布。

## 3.9 当前技术完成边界

当前技术成果应集中证明 Python 闭环能够真实运行和被验证。C 语言、数据结构及更多课程的课程包、练习与验证适配可以作为架构扩展方向，但不得在没有端到端证据时写成完成成果。

同样，统一身份认证、教师正式审核后台、生产级监控、大规模并发和复杂知识追踪模型不属于当前完成范围，应放入迭代计划。

## 5.1 第一阶段：比赛提交前的证据闭环

本阶段的目标不是继续堆叠功能，而是让已有 Python 闭环形成可核验、相互一致的比赛证据。

3. 使用最新部署版本录制 3 分钟以内的完整系统交互视频；

5. 补齐 AI 生成内容标识、隐私说明、数据使用说明和安全边界；
6. 统一计划书、PPT、演示视频、效果报告和线上系统中的功能名称与数据口径。

- 扩展更多 Python 知识点的专用课堂节拍和分级练习；
- 增加更多覆盖边界条件的代码任务与 Debug 任务；
- 完善阶段重测、学习前后变化和错误类型统计；
- 将最近对话、学习摘要和任务记录升级为服务端持久化；
- 改进键盘操作、窄屏适配、网络中断恢复和无障碍体验；
- 邀请计算机相关专业学生开展更贴近真实课程的连续使用测试。

## 5.3 第三阶段：扩展到其他计算机专业课程

在 Python 样板课程稳定后，再按照统一课程包规范逐步接入 C 语言和数据结构。每新增一门课程，都必须分别完成以下验收：

1. 课程目标、知识前置和来源审核；
2. 能力摸底与学习路径适配；
3. 课程问答检索与跨课程隔离；
4. 练习、Debug 和代码验证；
5. 学习画像更新和下一任务推荐；
6. 真实用户完整流程测试。

只有完成上述闭环，才将该课程写为“已打通”，避免把课程目录、知识点文件或单个页面误写成完整成果。

## 5.4 第四阶段：教师与院校应用

- 建立教师课程包编辑、审核和发布流程；
- 增加班级共性薄弱点、错误类型和学习进度分析；
- 接入学校统一身份认证和课程组织；
- 支持院校私有化部署、模型服务替换和现有教学平台接口集成；
- 在真实课程中开展连续性试点，并以匿名方式评估任务完成、重测变化和持续使用情况。

## 5.5 第五阶段：规模验证与策略升级

当平台积累足够、合规且匿名的连续学习序列后，再评估更复杂的知识追踪模型和推荐策略。在此之前继续使用透明、可审计的规则更新画像，避免用小样本训练结果制造不可靠的“智能评分”。

# 六、创新之处

## 6.1 创新一：以多智能体职责分离替代单模型自我循环

平台将学习规划、课程辅导和质量监督拆分为三个稳定职责，并为每个智能体设置不同的输入、输出和禁止事项。其创新不在于角色数量，而在于让“决定学什么、解释怎么学、检查能否发布”相互协同又相互制约。

可验证证据包括：结构化接口、三类智能体的独立测试、监督拒绝或降级记录，以及模型不能直接修改测试事实和画像的权限边界。

## 6.2 创新二：把学习行为转化为下一步可用证据

测评、练习、代码验证和重测不再只是一次结果，而是具有来源、时间、类型和权重的学习事件。画像更新与推荐都能说明使用了哪些证据，从而形成“行为—证据—画像—规划—新行为”的闭环。

可验证证据包括：事件 ID、画像更新前后状态、原因码、策略版本和下一任务推荐理由。

## 6.3 创新三：模型解释与确定性验证双轨运行

语言模型负责解释报错、生成分级提示和组织反馈，代码是否正确则由解释器、编译器、公开样例和隐藏测试决定。该分工既利用模型的语言能力，又避免模型成为无法审计的代码裁判。

可验证证据包括：相同代码的真实测试记录、模型反馈与测试事实一致性检查，以及模型无法覆盖通过状态的系统约束。

## 6.4 创新四：稳定课程骨架与个性化动态组课结合

平台不让模型临时生成整章教材，而是在经过审核的知识节点、课堂节拍和真实练习中，根据学生画像动态选择、删减和重排。这样既保证课程连续性，又能改变学习起点、讲解密度、练习难度和时间安排。

可验证证据包括：Python 课程知识节点、前置关系、阶段目标、不同画像生成的课堂差异和推荐理由。

## 6.5 创新五：角色化课堂共用同一可信知识链

教师、助教和同伴角色可以采用不同教学行为，但全部共享同一课程来源、引用校验和质量门禁。角色不是为了营造表面热闹，而是分别承担讲解、提示、提问、Debug 和总结等课堂职能。

可验证证据包括：同一问题在不同角色下的表达差异、共同引用来源和跨角色事实一致性测试。

## 6.6 创新六：从单门样板课程沉淀可复制的课程能力底座

项目当前只完整打通 Python，但在架构层将课程内容、知识来源、练习、测试、画像和智能体流程解耦。后续扩展课程的重点是替换并审核课程包，而不是复制一套新的前端和后端。

这项创新应以“可扩展设计和后续验证路径”表述，不能提前写成已经完成多课程规模化应用。

## 6.7 创新性的总体表述

本项目的创新不是把大模型包装成万能教师，而是把它放进一条有课程边界、有来源证据、有确定性裁决、有失败降级、有学习反馈的计算机课程学习系统中。平台追求的不是一次回答更像老师，而是一次学习行为能够被验证、被记录，并真正改变学生的下一步学习。

## 7.3 团队协作机制

团队围绕统一接口和可复现证据协作：

- 一个任务对应一名明确负责人；
- 公共字段和接口先形成契约，再由前后端并行实现；
- 每个功能同时提交实现、测试、文档和演示证据；
- AI 辅助生成的代码与课程内容仍由提交者审核；
- 课程事实、代码事实和用户数据分别由内容、测试和调研材料证明；
- 项目负责人统一核对计划书、PPT、视频、系统和效果报告的数据口径。

## 结语

多智能体协同学习平台希望解决的，不是学生是否拥有一个新的聊天框，而是学生能否获得连续、可信、适合自己的计算机专业课程学习过程。

当前项目从 Python 样板课程出发，先把能力摸底、个性化规划、结构化课堂、多角色辅导、代码验证、学习画像和下一任务推荐真正连接起来。后续再以同一能力底座逐门扩展课程、完善教师工具并开展真实教学试点。

**模型负责解释，证据负责决定；让每一次回答、每一段代码，都成为下一步学习的证据。**
