# ADR-0001：初步版本采用模块化单体

- 状态：已接受
- 日期：2026-08-10
- 决策者：项目组

## 背景

团队为5—6人，需要在三周内同时建设 C、Python、数据结构课程，并跑通多智能体、RAG、代码验证、学生画像和模型适配。若立即拆成多个服务，将增加接口协调、部署、观测和故障排查成本，压缩课程内容与学习闭环的时间。

## 决策

初步版本采用 Vue/Vite 前端和一个 FastAPI 模块化单体后端。后端内部按 `orchestration`、`rag`、`learner_profile`、`practice`、`model_adapters` 分模块，通过显式接口与共享契约协作；PostgreSQL/pgvector负责持久化与检索，Redis只承担必要的短期状态或缓存。

三个智能体作为编排模块中的逻辑角色存在，不各自部署为服务。所有外部模型经统一适配层访问。

## 理由

- 单套环境更容易在三周内开发、联调、演示和排错；
- 本地事务和统一数据模型降低学习闭环实现难度；
- 模块边界仍支持独立测试和多人并行；
- 避免为“多智能体”误建“多微服务”；
- 后续可根据实际性能、故障和团队边界再拆分，而非提前猜测。

## 后果

### 正面

- 部署单元少，开发反馈快；
- 契约和数据一致性更容易保证；
- 模型不可用时可在同一应用内降级；
- 课程能力能够复用同一业务引擎。

### 代价

- 模块隔离主要靠代码规范和测试，不是网络边界；
- 单个后端故障可能影响多个功能；
- 需要主动避免跨模块直接访问内部实现。

## 约束

- 跨模块数据通过公开服务接口或仓储接口访问；
- 共享Schema只在 `contracts/` 定义；
- 外部模型只能从 `model_adapters` 调用；
- 课程差异进入 `course_packs/`，不得复制业务模块；
- 为关键模块保留独立测试和超时/降级边界。

## 重新评估条件

仅当出现下列可观测需求时评估拆分：某模块需要独立扩缩容；代码运行需要强物理隔离；发布节奏明显不同；单体故障影响不可接受；或团队规模形成稳定独立负责边界。拆分前新增ADR记录数据所有权、接口与迁移方案。
